## 1. Goals & design principles

The portfolio reports answer four questions for a single game site (ZapGames.io, 1000games.io, …):

1. **Is the catalog concentrated?** What fraction of users and pageviews is driven by the top-X% of games?
2. **Where is the leverage?** Which games in the high-reach segment have low engagement (watchlist), and which mid-reach games have unusually high engagement (hidden gems)?
3. **How is the catalog composed?** Genre and tag distributions for the top segment.
4. **What should the editorial / growth team do next?** Tier-classified recommendations: promote flagships, feature niches, retire underperformers.

**Design principles:**

- **Two-source data model.** Catalog metadata (static-ish) comes from the per-site `*_all.csv`; engagement metrics (window-bounded) come from ClickHouse `gm_page_facts`. The reports are a **join** of these two.
- **Pareto-anchored analysis.** The report is always scoped to the top 20% of games by `users_with_as_top`. This is a deliberate cut — it captures the slice that explains 80%+ of traffic and is the only part worth ranking in detail. The full catalog is still counted in the concentration curve and headline stats.
- **Ratios, not absolutes.** Cross-game comparisons are always done via ratios (`eng_pct`, `avg_top_share`, percentile ratios) rather than absolute counts, because the engagement source (`gm_page_facts`) is a partial sample (~26% of v2 coverage per `methodology_v3.md`).
- **Reproducible.** Every output is generated by a single Python script with a fixed date window and no CLI arguments. Re-running the script with the same inputs yields byte-identical output. The mega-query is similarly fixed-template.
- **Auditable.** Every number in the report is traceable to (a) a row in a CSV, (b) a value computed in the Python script, or (c) a ClickHouse result in the engagement query log. There are no "magic" numbers.

## 3. Stage 1 — Catalog crawl (`*_all.csv`)

### 3.1 Source

The catalog is built by crawling the site's `sitemap.xml` and (where available) a Wayback Machine snapshot. For ZapGames, the recrawl was performed against `https://zapgames.io/sitemap.xml`; for 1000games, against `https://1000games.io/sitemap.xml`. The recrawl was not a custom script for this report — the CSVs were provided as inputs and the structure is documented in the methodology v3 file.

### 3.2 Schema (12 columns)

| Column | Type | Meaning |
|---|---|---|
| `slug` | string | URL-safe identifier; unique key for joins |
| `name` | string | Display name (often "Game 1", "Game 2" for SEO spam; usually clean) |
| `category` | string | Site-defined category — **populated for ZapGames, mostly empty for 1000games** |
| `genre` | string | Site-defined genre (`action`, `sports`, `arcade`, `multiplayer`, `simulation`, `casual`, `horror`, `puzzle`, `rpg`, `strategy`, `education`, `1000games` for 1000games-only bucket) |
| `tags` | string | Pipe-separated list of tags (e.g. `Skill Games\|Multiplayer Games\|Fast Paced Games`) |
| `image` | string | URL of cover image |
| `datePublished` | ISO date | First index date of the page |
| `desc` | string | HTML description (sometimes auto-generated: "Inferred from N user(s) with M total pageviews") |
| `users_with_as_top` | int | Number of unique users for whom this game was their **top game** in the crawl window — see §3.3 |
| `total_pv` | int | Total pageviews for the game's page during the crawl window |
| `top_game_pv` | int | Pageviews where this game was the user's top game |
| `avg_top_share` | float (0-1) | Mean of `top_game_pv / total_pv` across users who ranked this game top — see §3.3 |

### 3.3 `users_with_as_top` and `avg_top_share` — the ranking metric

These two columns are the **ranking metric** for the report. The motivation:

- `total_pv` is dominated by search-driven traffic and includes pageviews from users who never actually engaged with the game (landed, bounced).
- `users_with_as_top` is a proxy for **active fan-base size** — the number of users whose behavior showed enough sustained interest that this game became their *top* game. It is the right metric to rank by if the question is "which games actually have an audience on this site."
- `avg_top_share` is the average (across those top-ranking users) of how often this game was the top game out of all their pageviews. A high `avg_top_share` (>0.5) means users come back to this game repeatedly; a low one (~0.3) means they top-rank it once and then drift to other games.

**Filter applied at Stage 3:**

```python
all_rows = [r for r in zap if r["users_with_as_top"]]
```

Rows with empty / zero `users_with_as_top` are excluded from analytics. This is mostly defensive — every real game in the crawls has at least one user — but it guarantees the report's N is well-defined.

### 3.4 Catalog size

| Site | Rows in CSV | Rows with `users_with_as_top > 0` | Top 20% |
|---|---:|---:|---:|
| zapgames.io | 1,046 | 1,046 | 209 |
| 1000games.io | 485 | 485 | 97 |

## 4. Stage 2 — Engagement mega-query (`*_p50p90_engpct.csv`)

This stage is governed by `methodology_v3.md` (the v3 engagement methodology). The mega-query is a per-site adaptation of the v3 template; the only changes are:

- `site_id` literal
- the `extractAll(page_location, '...\.io/([a-z0-9][a-z0-9-]+)')` regex to extract slugs from URLs
- the WHERE-clause filter on `page_location LIKE '%<site>.io/%'`
- grouping by `slug` (extracted) instead of by `page_location`

### 4.1 Why two queries (not one)

The v3 template computes everything per `page_location`, but for a portfolio report we need everything per **slug**, which requires extracting the slug from the URL via `extractAll`. Combining the duration query and the engagement query into one would require a self-join or sub-select, which performs worse and is harder to read. The mega-query runs them as two sequential ClickHouse queries and joins the results in Python.

### 4.2 Query A — duration percentiles

```sql
WITH raw_per_meas AS (
    SELECT client_id, session_id, measurement_id,
           argMinMerge(page_location) AS page_location,
           sum(engagement_msec) / 1000.0 AS page_dur_s
    FROM gm_page_facts
    WHERE site_id = 'zapgames.io'             -- or '1000games.io'
      AND first_shard_date BETWEEN '2026-09-10' AND '2026-10-08'
      AND client_id != '' AND session_id != ''
    GROUP BY client_id, session_id, measurement_id
),
with_slug AS (
    SELECT
        client_id, session_id, page_dur_s,
        extractAll(page_location, 'zapgames\.io/([a-z0-9][a-z0-9-]+)') AS slug_arr
    FROM raw_per_meas
    WHERE page_location LIKE '%zapgames.io/%'   -- or '1000games.io/%'
),
slugs_only AS (
    SELECT client_id, session_id, page_dur_s, arrayJoin(slug_arr) AS slug
    FROM with_slug
    WHERE length(slug_arr) > 0
),
sess AS (
    SELECT slug, client_id, session_id, sum(page_dur_s) AS sess_dur
    FROM slugs_only
    GROUP BY slug, client_id, session_id
)
SELECT
    slug,
    count() AS sessions,
    uniqExact(client_id) AS users,
    round(quantile(0.5)(sess_dur), 2) AS s_p50,
    round(quantile(0.9)(sess_dur), 2) AS s_p90,
    round(avg(sess_dur), 2) AS s_avg
FROM sess
GROUP BY slug
ORDER BY users DESC
```

Output columns: `slug, sessions, users, s_p50, s_p90, s_avg`.

### 4.3 Query B — engagement rate

```sql
WITH raw_per_meas AS (
    SELECT client_id, session_id, measurement_id,
           argMinMerge(page_location) AS page_location,
           sum(engagement_msec) / 1000.0 AS page_dur_s
    FROM gm_page_facts
    WHERE site_id = 'zapgames.io'
      AND first_shard_date BETWEEN '2026-09-10' AND '2026-10-08'
      AND client_id != '' AND session_id != ''
    GROUP BY client_id, session_id, measurement_id
),
with_slug AS (
    SELECT
        client_id, session_id, page_dur_s,
        extractAll(page_location, 'zapgames\.io/([a-z0-9][a-z0-9-]+)') AS slug_arr
    FROM raw_per_meas
    WHERE page_location LIKE '%zapgames.io/%'
),
slugs_only AS (
    SELECT client_id, session_id, page_dur_s, arrayJoin(slug_arr) AS slug
    FROM with_slug
    WHERE length(slug_arr) > 0
),
sess AS (
    SELECT slug, client_id, session_id, sum(page_dur_s) AS sess_dur
    FROM slugs_only
    GROUP BY slug, client_id, session_id
),
per_user AS (
    SELECT slug, client_id, sum(sess_dur) AS user_dur
    FROM sess
    GROUP BY slug, client_id
)
SELECT
    slug,
    count() AS users_total,
    sum(if(user_dur > 30, 1, 0)) AS eng_users
FROM per_user
GROUP BY slug
ORDER BY users_total DESC
```

Output columns: `slug, users_total, eng_users`.

### 4.4 Python-side merge & write

```python
metrics = {}
for r in data['rows']:                       # Query A result
    metrics[r['slug']] = {
        'sessions': r.get('sessions', ''),
        's_p50':    r.get('s_p50', ''),
        's_p90':    r.get('s_p90', ''),
        's_avg':    r.get('s_avg', ''),
    }
for r in data2['rows']:                      # Query B result
    s = r['slug']
    if s not in metrics: metrics[s] = {}
    users = int(r.get('users_total', 0) or 0)
    eng   = int(r.get('eng_users', 0)   or 0)
    metrics[s]['users_eng'] = users
    metrics[s]['eng_users'] = eng
    metrics[s]['eng_pct']   = round(eng * 100.0 / users, 2) if users > 0 else ''
```

`eng_pct` is **the share of users with total time on the game > 30s**, computed at the user level (sum of all sessions for that user on that game), not the session level. A user with 3 sessions of 15s each (45s total) is engaged; a user with 1 session of 60s and 5 sessions of 0.5s is engaged. A user with one 29s session is not.

### 4.5 Output schema (`*_p50p90_engpct.csv`)

| Column | Source | Meaning |
|---|---|---|
| `slug` | — | Join key |
| `name`, `genre` | catalog CSV | Convenience columns for human reading |
| `users_with_as_top`, `total_pv`, `top_game_pv`, `avg_top_share` | catalog CSV | Catalog metrics carried through |
| `sessions` | Query A | Sessions where the page_location matched this slug |
| `users_eng` | Query B (= `users_total`) | Unique users with at least one measurement on this game's page |
| `eng_users` | Query B | Subset of `users_eng` with `user_dur > 30s` |
| `eng_pct` | derived | `eng_users / users_eng × 100` |
| `s_p50`, `s_p90`, `s_avg` | Query A | Per-session duration percentiles (seconds) |
| `matched` | derived | `Y` if the engagement query returned a row for this slug, else `N` |

### 4.6 Coverage expectation

For ZapGames, all 209 top-20% slugs matched (`matched=Y`). For 1000games, all 97 matched. This is the v3 coverage *within* the catalog — the v3 vs v2 coverage gap (~74%) is documented in `methodology_v3.md` and is **already absorbed** into these numbers; we do not normalize further.

### 4.7 Why the 28-day window

The window is fixed at `2026-09-10 → 2026-10-08` (28 days). This matches the most recent fully-materialized `gm_page_facts` window at report-generation time. The window is **hard-coded in the mega-query and in the report generator** — it is not a parameter, to keep the report outputs reproducible.

## 5. Stage 3 — Join & metric definitions

In `<site>_generate_report.py`:

```python
zap = list(csv.DictReader(open(CSV, encoding="utf-8")))
metrics = list(csv.DictReader(open(MET, encoding="utf-8")))
m_by_slug = {r["slug"]: r for r in metrics}

rows = []
for r in zap:
    if r["slug"] in m_by_slug:                       # keep only top-20%
        m = m_by_slug[r["slug"]]
        rows.append({
            "slug": r["slug"], "name": r["name"],
            "genre": r["genre"], "tags": r["tags"],
            "users_with_as_top": int(r["users_with_as_top"] or 0),
            "total_pv":          int(r["total_pv"] or 0),
            "top_game_pv":       int(r["top_game_pv"] or 0),
            "avg_top_share":     float(r["avg_top_share"] or 0),
            "sessions":          int(m.get("sessions") or 0),
            "users_eng":         int(m.get("users_eng") or 0),
            "eng_users":         int(m.get("eng_users") or 0),
            "eng_pct":           float(m.get("eng_pct") or 0),
            "s_p50":             float(m.get("s_p50") or 0),
            "s_p90":             float(m.get("s_p90") or 0),
            "s_avg":             float(m.get("s_avg") or 0),
        })
```

### 5.1 Metric dictionary (in the report)

| Metric | Definition | Units | Source |
|---|---|---|---|
| **users_with_as_top** | Unique users for whom this game was their top game in the catalog window | users | catalog CSV |
| **total_pv** | Total pageviews for this game's page | pageviews | catalog CSV |
| **top_game_pv** | Pageviews where this game was the user's top game | pageviews | catalog CSV |
| **avg_top_share** | Mean of `top_game_pv / total_pv` across the game's top-ranking users | ratio [0-1] | catalog CSV |
| **sessions** | Sessions in `gm_page_facts` with a `page_location` matching this slug | sessions | ClickHouse |
| **users_eng** | Unique clients with at least one measurement on this page | users | ClickHouse |
| **eng_users** | Subset of `users_eng` where total time on page > 30s | users | ClickHouse |
| **eng_pct** | `eng_users / users_eng × 100` | % | derived |
| **s_p50** | Median per-session duration | seconds | ClickHouse |
| **s_p90** | 90th-percentile per-session duration | seconds | ClickHouse |
| **s_avg** | Mean per-session duration | seconds | ClickHouse |

### 5.2 Sort order

After the join, `rows` is sorted in **descending order of `users_with_as_top`**. This sort order is the single source of truth for ranking throughout the rest of the report — headline acts, tier classification, watchlist picks.

## 6. Stage 4 — Concentration curve (Pareto check)

### 6.1 Purpose

The concentration curve answers: **what share of users / pageviews / top-game pageviews is captured by the top X% of the catalog?** If the catalog is Pareto-distributed, the top 20% should carry ~80% of the value.

### 6.2 Computation

```python
rows.sort(key=lambda r: r["users_with_as_top"], reverse=True)
N_TOTAL = len(rows)
total_U  = sum(r["users_with_as_top"] for r in rows)
total_PV = sum(r["total_pv"]          for r in rows)
total_TG = sum(r["top_game_pv"]       for r in rows)

def cum_share(take_n, key):
    sub = rows[:take_n]
    s = sum(r[key] for r in sub)
    return s, 100.0 * s / max(1, sum(r[key] for r in rows))

for pct in (0.05, 0.10, 0.20, 0.30, 0.50, 1.00):
    n = max(1, round(N_TOTAL * pct))
    u,  ushare = cum_share(n, "users_with_as_top")
    pv, pvshare = cum_share(n, "total_pv")
    tg, tgshare = cum_share(n, "top_game_pv")
```

### 6.3 Slices reported

The report always shows six slices: **top 5%, 10%, 20%, 30%, 50%, 100%**. The 20% slice is the headline ("Pareto check") and the 100% row is included to make the cumulative shares obviously total 100%.

### 6.4 Reading the curve

| Reading | Interpretation |
|---|---|
| Top 20% carries ~80% of users | **Pareto holds** — the catalog is doing what 80/20 catalogs do. |
| Top 20% carries >85% of users | **Hyper-Pareto** — concentration is even tighter than classic. The portfolio is a few stars + a long tail. |
| Top 20% carries <70% of users | **Anti-Pareto** — the catalog is unusually balanced; the long tail is pulling weight. |
| Top 20% carries ~80% of users but only 60% of top-game PV | **Engagement is fragmented** — reach is concentrated but in-game activity is more spread out. |
| Top 20% carries 80% of users but 95% of top-game PV | **Engagement is concentrated harder than reach** — the top games don't just have more users, they have more engaged users per capita too. |

### 6.5 Observed values

| Site | Top 20% (N) | % users | % PV | % top_game_pv |
|---|---:|---:|---:|---:|
| ZapGames | 209 | 80.7% | 81.3% | n/a (not reported in v3) |
| 1000games | 97 | 82.8% | 85.1% | 87.1% |

Both sites are in the **Pareto to mild-hyper-Pareto** range. 1000games is slightly more concentrated than ZapGames at the 20% mark.

## 7. Stage 5 — Tier classification

### 7.1 Why tiers

The top 20% of the catalog is still 209 / 97 games — too many to act on individually. Tiers reduce the list to four actionable buckets, each with a different growth-team play:

| Tier | Definition | Action |
|---|---|---|
| **T1_Star** | High eng% + high reach | **Flagships** — anchor homepage, brand definition, exclusive promotion |
| **T2_Niche_Loyal** | High eng% + low reach | **Discovery candidates** — cross-promote, feature in related-game widgets, tag aggressively |
| **T3_Discovery** | Low eng% + high reach | **Search magnets** — keep for SEO, but don't editorialize as "good games" |
| **T4_Underperformer** | Low eng% + low reach | **Sunset candidates** — retire, redesign, or replace |

### 7.2 Two axes, one cut

The 1000games report uses a **rank + absolute-volume** hybrid:

```python
def tier(rank, n):
    if rank <= n * 0.20:                       return "T1_Star"
    if r["users_with_as_top"] >= 1000:         return "T1_Star"
    if rank <= n * 0.50:                       return "T2_Niche_Loyal"
    if r["users_with_as_top"] >= 300:          return "T2_Niche_Loyal"
    if rank <= n * 0.75:                       return "T3_Discovery"
    if r["users_with_as_top"] >= 100:          return "T3_Discovery"
    return "T4_Underperformer"
```

Where `n` is the size of the top-20% slice and `rank` is the 1-indexed position in `users_with_as_top` order.

The ZapGames report uses a **2-D quadrant** definition:

| | eng% ≥ 50% | eng% < 50% |
|---|:---:|:---:|
| **users_eng ≥ median (538)** | T1_Star (58) | T3_Discovery (45) |
| **users_eng < median** | T2_Niche_Loyal (58) | T4_Underperformer (48) |

### 7.3 Why two implementations

The two reports were built on slightly different versions of the helper logic. The 2-D quadrant (ZapGames) is **more theoretically defensible** (it's a real scatter-plot quadrant, axes are interpretable) but is sensitive to the median cutoff, which is only defined within the top-20% segment. The rank+volume hybrid (1000games) is **more robust for smaller segments** (97 games is too small for a clean 2-D median split) and produces a more interpretable list for a smaller catalog.

**Recommendation for future reports:** use the 2-D quadrant if the top-20% segment has ≥ 200 games; use the rank+volume hybrid if it has < 200.

### 7.4 Edge cases

- **Boundary games (exactly at the median or threshold):** always classified into the higher tier. E.g. a game with `eng_pct = 50.0` and `users_eng = 538` is T1_Star in the ZapGames schema.
- **Missing engagement data:** a slug that appears in the catalog but not in `*_p50p90_engpct.csv` is excluded from tier classification. In the current runs, every top-20% slug matched, so this never fires — but the report generator is safe-by-default: missing metrics are coerced to 0 and the game falls into T4_Underperformer.
- **Discovery Hub anomalies:** ZapGames' `gta-5-online` is a T3_Discovery Hub — 71,785 users_eng, 16.9% eng%. It's not a "bad" game; it's a search-driven landing page. The T3 tier correctly captures it.

## 8. Stage 6 — Genre & tag breakdowns

### 8.1 Genre breakdown

```python
genre_buckets = collections.defaultdict(lambda: {"games": 0, "users": 0, "pv": 0, "tg": 0})
for r in top20:
    g = (r["genre"] or "(none)").strip() or "(none)"
    genre_buckets[g]["games"] += 1
    genre_buckets[g]["users"] += r["users_with_as_top"]
    genre_buckets[g]["pv"]    += r["total_pv"]
    genre_buckets[g]["tg"]    += r["top_game_pv"]
genre_rows = sorted(genre_buckets.items(), key=lambda kv: kv[1]["users"], reverse=True)
```

The genre table in the report has 4 measure columns (`games, users, pv, top_game_pv`) and 4 share columns (`% of top-20% users, % of top-20% PV, % of top-20% top_game_pv`). Shares are computed against the **top-20% total** (not the full catalog), because the table is meant to show composition of the analyzed segment.

### 8.2 Tag breakdown

Tags are pipe-separated in the catalog CSV. The parser:

```python
for r in top20:
    raw = (r["tags"] or "").strip()
    if not raw: continue
    for t in [x.strip() for x in raw.split("|") if x.strip()]:
        tag_buckets[t]["games"].add(r["slug"])
        tag_buckets[t]["users"] += r["users_with_as_top"]
```

Important: `games` is a **set** (a tag is counted once per game even if it appears in multiple rows — defensive, though in practice each (game, tag) pair is unique). `users` is **summed across rows**, so a user with two top games both tagged `Skill Games` contributes 2 to the user count. This is a deliberate choice — it captures **co-occurrence weight** — but it means tag user counts can exceed the top-20% total user count.

The ZapGames tag report (`zapgames_portfolio_tags.csv`) follows the same pattern. The 1000games report shows the top 25 tags in the markdown (the full 59 are in the CSV).

### 8.3 Tag-level caveat

Summed users across tags is a co-occurrence metric, not a reach metric. It tells you "this tag is associated with this much user activity across the catalog" — useful for prioritization of new uploads, less useful for headcounting. The ZapGames report includes a **3-tag top-3 most-attached** summary (`3D` 63%, `Challenge` 55%, `Survival` 26%) to give a quick composition read.

## 9. Stage 7 — Watchlist & hidden-gems heuristics

These two tables answer the same question from opposite directions: **where is the gap between reach and engagement?**

### 9.1 Watchlist — high reach, low engagement

```python
watchlist = []
for r in top20:
    if r["eng_pct"] > 0 and r["users_with_as_top"] >= 200:
        watchlist.append(r)
watchlist.sort(key=lambda r: r["eng_pct"])
watchlist = watchlist[:10]
```

- **Universe:** all top-20% games with positive eng_pct and at least 200 users (to avoid recommending engagement work on tiny-audience games)
- **Sort:** ascending by `eng_pct` (lowest engagement first)
- **Output:** top 10

The watchlist is a list of games where the audience is there but the engagement isn't — these are the highest-leverage games for product work (better onboarding, tighter first-session loop, more game modes, etc.).

### 9.2 Hidden gems — high engagement, mid audience

```python
gems = [r for r in top20 if r["eng_pct"] > 0 and 50 <= r["users_with_as_top"] <= 600]
gems.sort(key=lambda r: r["eng_pct"], reverse=True)
gems = gems[:10]
```

- **Universe:** all top-20% games with 50 ≤ users_with_as_top ≤ 600 (small but non-trivial audience; high-engagement stars with thousands of users are already T1 and don't need surfacing)
- **Sort:** descending by `eng_pct`
- **Output:** top 10

Hidden gems are the "promote me" list — games whose users love them but whose reach is small. They are the candidates for cross-promotion from T1 stars, homepage feature slots, or "trending" rotation.

### 9.3 Why these thresholds

- **`eng_pct > 0`:** defensive; the report generator coerces missing values to 0, and a 0-eng% game is uninteresting in both lists
- **`users_with_as_top >= 200` (watchlist):** below 200, engagement is dominated by noise from very small samples
- **`50 ≤ users ≤ 600` (gems):** the lower bound excludes pure noise; the upper bound excludes games that are already big enough to be T1_Star (where the recommendation is "keep doing what you're doing," not "surface this game")

The thresholds are **hard-coded**, not derived from the data, to keep the heuristics interpretable. If the report audience wants data-driven thresholds, the natural next step is to use the top-20% median + 1 MAD or similar, but that adds complexity for marginal gain.

## 10. Stage 8 — Markdown report assembly

The report is built as a list of lines and written at the end. Sections, in order:

1. **Header** — site, window, generated date, source files
2. **§1 Executive summary** — five to seven bullet headlines
3. **§2 Concentration** — six-slice table + 2-3 sentence interpretation
4. **§3 Tier classification** — definition table (rank+volume hybrid or 2-D quadrant)
5. **§4 Headline acts** — top 10 by `users_with_as_top` with all engagement columns
6. **§5 Genre breakdown** — full table sorted by users descending
7. **§6 Top tags** — top 25 (1000games) or top 30 (ZapGames)
8. **§7 Engagement deep-dive** — distribution stats: median, mean, min, max of `eng_pct`, `s_p50`, `s_p90`, `s_avg`
9. **§8.1 Watchlist** + **§8.2 Hidden gems**
10. **Footer** — file inventory + methodology glossary

### 10.1 Formatting conventions

- All percentages in tables are formatted `XX.X%` (one decimal)
- All counts in tables are formatted with thousands separators (`1,046`, `209,088`)
- All durations are formatted `XX.Xs` (one decimal, suffixed `s`)
- `eng_pct` is shown with `%` suffix; `avg_top_share` is shown as a 3-decimal float (0.406)
- Tier names are always `T1_Star`, `T2_Niche_Loyal`, `T3_Discovery`, `T4_Underperformer` — no abbreviations
- Slugs are always wrapped in backticks (\`slug\`) so they render as code
- Section headings use `##` (one level deep) and `###` for sub-sections; numbered `## 1.`, `## 2.`, … for top-level sections
- Bullet separators in tier-split lines use the middle dot `·` (U+00B7) — not a hyphen

### 10.2 What the markdown is *not*

- It is **not** a fresh analysis each run. It is a deterministic rendering of the joined data.
- It is **not** the source of truth for any number. Every number in the markdown can be re-derived from `*_all.csv` + `*_p50p90_engpct.csv` + the generator script.

## 12. Quality control & validation

### 12.1 Pre-flight checks (in the mega-query script)

After the mega-query, the script prints:

- N slugs in the catalog (with `users_with_as_top > 0`)
- N slugs in the top-20%
- Row count returned by each ClickHouse query
- N matched slugs (slug in both catalog top-20% and engagement result)

Expected: matched = top-20% count. If matched < top-20%, the report must be re-run after investigating the missing slugs.

### 12.2 Sanity checks (in the report generator)

- **Concentration sum** must be 100% for the "All" row.
- **Tier counts** must sum to the top-20% count.
- **Watchlist + gems** each return at most 10 rows.
- **Genre counts** (sum of `games` column) must equal the top-20% count.
- **Markdown render** is not silently truncated — total line count is logged.

### 12.3 Independent re-derivation (recommended after every run)

After generating a report, re-derive the concentration curve **independently in PowerShell** to confirm the report's numbers are correct:

```powershell
$rows = Import-Csv D:\GR\zapgames_all.csv
$rows = $rows | Where-Object { $_.users_with_as_top -as [int] -gt 0 }
$rows = $rows | Sort-Object {[int]$_.users_with_as_top} -Descending
$n = $rows.Count
$totalU = ($rows | Measure-Object users_with_as_top -Sum).Sum
$totalPV = ($rows | Measure-Object total_pv -Sum).Sum

function row($label, $take) {
  $sub = $rows | Select-Object -First $take
  $u = ($sub | Measure-Object users_with_as_top -Sum).Sum
  $pv = ($sub | Measure-Object total_pv -Sum).Sum
  "{0,-12} N={1,4} ({2,4:N1}%)  users={3,6:N1}%  PV={4,5:N1}%" -f $label, $take, (100*$take/$n), (100*$u/$totalU), (100*$pv/$totalPV)
}
row "Top 5%"   ([int]($n*0.05))
row "Top 10%"  ([int]($n*0.10))
row "Top 20%"  ([int]($n*0.20))
row "Top 30%"  ([int]($n*0.30))
row "Top 50%"  ([int]($n*0.50))
```

Expected: matches the report's `§2 Portfolio concentration` table exactly.

### 12.4 UTF-8 handling

Both the report and this methodology doc are written as UTF-8. The middle dot (`·`), em dash (`—`), and `≥` characters may display incorrectly in **PowerShell's default code page (Windows-1252)** when reading with `Get-Content` — this is a console-display issue, not a file issue. The files are correctly UTF-8 and will render normally in Cursor, VS Code, browsers, and GitHub.

## 13. Known caveats & limitations

### 13.1 Engagement source coverage (v3)

`gm_page_facts` captures only ~26% of full v2 traffic. This is **documented in `methodology_v3.md` and is the canonical reference for this caveat.** Concretely:

- `users_eng`, `eng_users`, `sessions` will run lower than the equivalent v2 query.
- Ratios (`eng_pct`, percentile ratios) are valid for cross-game comparison.
- p50/p90 are valid as **distributional summaries**, not as absolute session-length measurements.
- Do not compare ZapGames or 1000games absolute engagement numbers with v1/v2 numbers from older reports.

### 13.2 `users_with_as_top` is a ranking proxy, not a reach metric

It measures the number of users for whom this game became their *top* game in the catalog crawl window. It is **not** the same as `users_eng` (the 28-day ClickHouse unique users on this page). They correlate, but `users_eng` includes search-traffic-only users who never rank the game top. Use `users_with_as_top` for **ranking** and `users_eng` for **engagement context**.

### 13.3 The 28-day window is fixed

The window `2026-09-10 → 2026-10-08` is hard-coded in both the mega-query and the report generator. Updating the window requires:

1. Editing `START` and `END` constants in the mega-query script
2. Editing the same constants in the report generator
3. Re-running the mega-query
4. Re-running the report generator

There is no CLI argument parsing. This is intentional for reproducibility, but it does mean **the report goes stale** if the engagement data refreshes and the window is not bumped.

### 13.4 No bot filter in v3

The v3 source table has no `bot` column. The ZapGames report's `> Methodology caveat (v3)` callout is the canonical place to flag this for readers. Bot filtering happens upstream in the `gm_page_facts` materialization; we don't apply it again here.

### 13.5 Tier classification has implementation drift

ZapGames uses the 2-D quadrant; 1000games uses rank+volume. The classification labels match, but the underlying logic differs. See §7.3 for the rule of thumb on which to use for which catalog size.

### 13.6 Genre is empty for 1000games games (the `1000games` bucket)

Six 1000games top-20% games have `genre = "1000games"` (not a real genre — a side-effect of the crawl tagging all games on the site with the site name as a category). These get their own row in the genre table; they're real games with real users, just lacking a clean genre assignment.

### 13.7 Watchlist and hidden-gems thresholds are hard-coded

See §9.3. If the catalog or window changes drastically, re-tune the `200` and `50-600` thresholds. The current values were chosen for the 97-209 game top-20% segments; they would need adjustment for catalogs that are an order of magnitude larger or smaller.

### 13.8 The 1000games report has no "tier-by-tier top-10" deep-dive

The ZapGames report (§6.1-6.4) shows top-10 within each tier. The 1000games report does not — it shows only the tier counts and the overall top 10. This is a deliberate scope difference: the ZapGames report is the deeper one and was generated first; the 1000games report is the lighter adaptation.

## 14. Operational runbook

### 14.1 To regenerate the ZapGames report from scratch

```powershell
# 1. Make sure zapgames_all.csv is current
# 2. Make sure gma_client.py is on PYTHONPATH (D:\GR)
# 3. Re-run the engagement mega-query
cd D:\GR

$rows = Import-Csv D:\GR\zapgames_all.csv
$rows = $rows | Where-Object { $_.users_with_as_top -as [int] -gt 0 }

# ... (see §12.3 for the rest)

# 6. Spot-check the engagement CSV
Get-Content D:\GR\zapgames_p50p90_engpct.csv -TotalCount 5
(Get-Content D:\GR\zapgames_p50p90_engpct.csv | Measure-Object -Line).Lines
# Expected: header + 209 data rows = 210 lines
```

### 14.2 To generate a report for a new site

1. Create `<site>_all.csv` (12 columns per §3.2) by recrawling the sitemap.
2. Copy `1000games_query_mega.py` → `<site>_query_mega.py` and edit:
   - `SITE` constant
   - the `1000games` literal in the SQL (both `extractAll` regex and `LIKE` filter)
3. Copy `1000games_generate_report.py` → `<site>_generate_report.py` and edit:
   - all input/output paths
   - `SITE`, `START`, `END` constants
   - markdown report's site name in the H1
4. Run the mega-query; confirm matched = top-20% count.
5. Run the report generator; verify outputs.
6. Run the §12.3 independent verification.

### 14.3 To translate the report

The reports have a stable structure (eight numbered sections plus a footer). Translation can be done mechanically: translate prose / headings / recommendations / methodology text, but **do not** translate slugs, tag names, genre names, tier names, file paths, metric column names, or any numbers. See the Vietnamese translation `1000games_portfolio_report.vi.md` and `zapgames_portfolio_report.vi.md` for a worked example.

## 16. Glossary

| Term | Meaning |
|---|---|
| **Catalog** | The full list of game pages on a site (e.g. 1,046 for ZapGames) |
| **Top 20% / Pareto slice** | The 209/97 games with the highest `users_with_as_top`. The analyzed segment. |
| **`users_with_as_top`** | Unique users for whom this game was their top game in the catalog window. **Ranking metric.** |
| **`users_eng`** | Unique users with at least one measurement on this game's page in the engagement window. **Reach metric (in the engagement context).** |
| **`eng_users`** | Subset of `users_eng` with total time on page > 30s |
| **`eng_pct`** | `eng_users / users_eng × 100` — engagement rate |
| **`s_p50` / `s_p90`** | Median / 90th-percentile per-session duration (seconds) |
| **Pareto** | The 80/20 pattern: 20% of the catalog carrying ~80% of users |
| **Concentration curve** | Cumulative share of users / PV / top-game PV by catalog percentile |
| **Tier** | One of T1_Star / T2_Niche_Loyal / T3_Discovery / T4_Underperformer |
| **T1_Star** | High eng% + high reach — flagships |
| **T2_Niche_Loyal** | High eng% + low reach — discovery candidates |
| **T3_Discovery** | Low eng% + high reach — search magnets / landing pages |
| **T4_Underperformer** | Low eng% + low reach — sunset candidates |
| **Watchlist** | High-reach, low-engagement games — high leverage for product work |
| **Hidden gem** | High-engagement, mid-reach games — candidates for surfacing |
| **Mega-query** | The two-query ClickHouse batch that produces `*_p50p90_engpct.csv` |
| **GM page facts** | The ClickHouse pre-aggregated table used as the v3 engagement source (see `methodology_v3.md`) |
| **V3 methodology** | The current engagement source = `gm_page_facts`. Defined in `methodology_v3.md`. |
